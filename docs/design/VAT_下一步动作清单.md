## 一 · P0：阻塞「真实可用」的硬卡点（先做）

### A1 · DEV 轮真实产出打通（当前唯一卡点）
- **现状**：PM 轮已通；DEV 轮（大编码任务）卡在 glm-5.3-flash 强制深度思考，思考流耗尽预算后 JSON 信封从未产出 → 解析失败。4 轮加固（16k 预算 / 思考简短指令 / 信封提取 / 裸换行修复）仅让 PM 级小任务走通，DEV 级仍不稳。
- **根因**：非引擎缺陷，是「与该模型思考习惯对抗性价比低」。
- **具体动作**：执行 v0.3 #8——写模型探测脚本，对中转 23 个候选模型逐一测 `content` 通道能否输出结构化 JSON，选定**走正常 content 通道的主力模型**，替换当前 glm-5.3-flash。
- **完成标准**：一句话需求 → `vat run --mode draft` 全链 PM→DEV→REVIEW→QA 至 done，单据 `source:llm` 真实落盘，无解析失败。
- **依赖**：A2（探测脚本即 #8 本体）。

### A2 · 模型探测脚本沉淀为常驻能力（v0.3 #8）
- **现状**：#8 标记为「📋 下一步第一项」，尚未实现。
- **具体动作**：将探测逻辑固化为 `vat doctor --probe-models`，输出每个模型的「content 通道是否产出结构化 JSON / 思考型行为 / 可用角色」矩阵。
- **完成标准**：`vat doctor --probe-models` 一键跑完 23 模型并生成可用主力推荐；风险登记 #1 闭环。
- **依赖**：无。

### A3 · 真实 e2e 全链验收（v0.3 #7）
- **现状**：⏳ PM 过，DEV 卡于模型问题。
- **具体动作**：A1/A2 完成后，跑通完整 draft 链路并补 e2e 测试夹具（golden-path 升级为「真实模型」版）。
- **完成标准**：V1 完成定义达成——一句话需求 → 卡片 done，账本逐笔真实 usage，429 场景冷却续跑。
- **依赖**：A1、A2。

## 二 · P1：工程完善（V1 收尾 + 健壮性）

### B1 · 接入指南文档（v0.3 #6）
- **现状**：⏳ `vat models` / `doctor --network` 命令已交付，但 README 接入指南待写。
- **具体动作**：在 README 补「接真实模型」章节（填 provider / `vat.config.json` / `apiKeyEnv` 环境变量 / 推荐主力模型结论）。
- **完成标准**：新人按文档 5 分钟内完成真实模型接入。
- **依赖**：A2（需先有主力模型结论）。

### B2 · 上下文预算对齐（v0.3 #9）
- **现状**：📋 待办。200k/256k 上下文时代，记忆注入默认值偏低。
- **具体动作**：`summaryWarnChars` 4000→12000、`decisionWindow` 20→50、`lessonWindow` 30→80；回归测试覆盖新阈值。
- **完成标准**：长会话下 PM/DEV 记忆注入不截断，决策/教训不丢失。
- **依赖**：无。

### B3 · 跨进程运行锁（v0.3 #10）
- **现状**：📋 待办。验证期间已暴露——两个 `vat run` 可能并发消费同一单据。
- **具体动作**：在 VAT Workspace 加 `.runlock`（PID + 心跳），启动时检测并拒绝/等待；崩溃后心跳超时自动释放。
- **完成标准**：并发 `vat run` 不再双消费同一单据；锁文件锁死时给出明确报错而非静默竞争。
- **依赖**：无。风险登记 #2 闭环。

### B4 · 提示注入持续复查（风险登记 #3）
- **现状**：XML 包裹 + 闸门白名单已缓解；待测真实运行后复查。
- **具体动作**：V1 真实运行后，定期检查 `_dead/` 无注入痕迹、单据 `source` 标注无异常；必要时加输入净化层。
- **完成标准**：真实多轮运行后 `_dead/` 无注入特征单据。
- **依赖**：A3（先有真实运行）。

## 三 · P2：演进路线（V2 / V3 / V4，按价值排序）

### C1 · V2 cli-executor：编排真实 Agent CLI（核心杠杆）
- **现状**：架构预留「(预留)CLI执行器」，v0.3-plan 标为「后续」，未实现。**这是「编排 AGENT 能力具象化」的真正落地点**。
- **具体动作**：
  1. 定义章程角色声明 `engine: llm | cli:<name>`；
  2. 实现 `cli-executor`：章程+单据写临时 prompt 文件 → `execa` spawn `claude` / `gemini` / `codex` CLI → 解析其产出（diff / 文件树 / 文本）；
  3. 混编验证：同一卡片内 PM(llm) + DEV(cli:claude) 跑通。
- **完成标准**：DEV 角色可由真实 coding agent CLI 承担，VAT 从「自己调 LLM」升级为「**编排真实 coding agent**」。
- **依赖**：A3（V1 链路先稳）。
- **价值**：直接回应你的工作流痛点——把「我指挥 agent 写代码」变成「VAT 调度真实 agent 写代码」，你退到卡点裁决位。

### C2 · V3 记忆自动压缩 + Dashboard 增强
- **现状**：v0.2 用阈值截断 + 手动压缩；Dashboard 无记忆查看器/单据全文/过滤。
- **具体动作**：LLM 驱动 `summary` 压缩（接 A2 探明的可用模型）；Dashboard 加记忆查看器、单据全文、过滤。
- **完成标准**：长项目记忆不爆窗口；看板可下钻任意卡片全文与历史决策。
- **依赖**：A2、B2。

### C3 · V4 分发
- **现状**：v0.2 npm 包分发（规划内）；`@vat/cli` bin / 便携 zip / Tauri 壳标为「后续」。
- **具体动作**：发布 `@vat/cli`（含 bin）；出便携 zip（内网/离线）；Tauri 壳（内置 Dashboard + 便携 Node，覆盖无 Node 环境）。
- **完成标准**：`npm i -g @vat/cli` 后终端直接用 `vat`；或下载 zip 解压即用。
- **依赖**：C1（引擎稳定后再做壳，避免锁发布节奏，见架构 §3.2 判断）。

### C4 · 闭环验证：用 VAT 管你自己的 Yestar 项目
- **现状**：VAT 目前是「工具」，尚未在真实业务项目上跑过完整周期。
- **具体动作**：选一个 Yestar 子项目（如 `Yestar_znq` 或 `yetsar_triage` 的新模块），用 VAT 走「提需求 → 编排 → 严格闸门 → 卡点裁决 → 签发」全链，记录 agent 实际节省的人工时。
- **完成标准**：产出一份「VAT 在真实项目上的提效报告」（提交数对比 / 拦截的 defect 数 / 你本人干预次数）。
- **依赖**：A3、C1。
- **价值**：把「编排能力具象化」从 demo 推进到「经业务验证」——这是你对外讲这个故事时最硬的证据。
