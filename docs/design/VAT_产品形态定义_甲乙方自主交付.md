# VAT 产品形态定义:甲乙方自主交付闭环

> 用户 2026-10-06 17:46 最终定义 | 取代"个人工作流增强层"窄定位,收敛为"面向非技术用户的自主软件交付产品"
> 与 `VAT_价值与差异化终审决策.md` 配套:本文件定义"产品长什么样",前文件定义"值不值得做"。

---

## 一、一句话定位

**VAT = 一个无需用户介入的虚拟软件交付公司。**

非技术用户(甲方 / 小白)只提模糊需求,VAT(乙方)内部 `PM → 主程 → X 个开发角色 → 测试 → 验收 → 部署` 全自动跑通,跨任务沉淀技能与记忆,下一轮增量需求直接复用。**期间完全不需要用户介入** —— 这是甲乙方模式的核心:甲方只管提需求和最终验收,过程全托管。

---

## 二、端到端闭环(10 阶段)

| # | 阶段 | 产出 / 动作 |
|---|---|---|
| 1 | 小白提需求 | 可极模糊(一句话 / 一段描述) |
| 2 | PM 多轮澄清提问 | 产出**完整 PRD**(范围 / 边界 / 验收标准) |
| 3 | 主程拆最小细粒度需求 | 任务卡片清单(可并行粒度) |
| 4 | 分出 X 个开发角色并行开发 | 各持独立会话窗 + `tasks/<id>/docs/` |
| 5 | 测试 | 单元 / 集成 / StrictRunner 闸门 |
| 6 | 主程 / PM 验收 | 循环:不达标回退对应角色重做,直到达成产品形态 |
| 7 | 部署 | 本地;或用户给了公网服务器 → 阿里云 / 腾讯云 |
| 8 | 反馈给用户验收 | 交付物 + 演示 |
| 9 | 阶段完成 | 归档 `archive/`,产出可审计账本 |
| 10 | 下一轮新需求(增量) | 复用既有技能 / 记忆,直接进入第 2 阶段 |

**关键约束**:第 1~9 阶段**默认无需用户(甲方)介入**(自治是默认态);仅当需求不确定时主动通知确认(见 §八 用户绑定与升级确认机制)。用户只在第 1 阶段输入、第 8 阶段验收,以及被叫应时确认。

## 三、每个角色沉淀的工件(跨任务资产)

| 工件 | 载体 | 作用 | 跨任务? |
|---|---|---|---|
| **统一 agent.md**(开发协议 / 规范) | 角色章程 | 权责 / 工具白名单 / 代码规范 / 接口契约 | ✅ 组织资产 |
| **任务短期记忆** | `tasks/<id>/docs/` | 本项目约束 / 决策,有界窗口不爆 | ❌ 任务级 |
| **任务长期记忆** | `memory/<ROLE>/` | 岗位 SOP / 通用教训,跨任务积累 | ✅ |
| **提炼技能(skills)** | 技能库 | "怎么造这类东西"蒸馏成可复用技能 | ✅ **最大护城河** |

> 第 4 节里的"技能库"是核心:它不是重新生成,而是从多次任务中**蒸馏出"怎么造 X"的方法论**。这正是现有 incumbent(每次从零生成)不做的事。

## 四、这如何改变"值不值得做"的判决

前文件 verdict = 条件性 GO(只作个人工作流增强层,不作通用框架)。本形态把它**升级为产品**:

- **护城河迁移**:从"记忆架构(功能级)"升级为"**非技术用户的自主交付闭环 + 跨任务技能沉淀(产品级)**"。
- **竞品迁移**:从"Anthropic / LangChain 编排框架"转为"**Lovable / Bolt / v0 / Replit Agent / Devin**"这条**非技术用户建应用**赛道 —— 2026 最拥挤、资金最厚。
- **VAT 能赢的切片**:持久员工(有工龄)+ 跨任务技能蒸馏 + 文件账本可接管。incumbent 多是 **stateless 生成**(每次从零),不做经验积累。这是 VAT 真正能立住的差异化。

## 五、反对意见(不捂盖子)

1. **"完全不需要用户介入"的陷阱已通过 §八 升级机制化解。** 原风险:PRD 解读偏离意图时全自动会造出"精美但错误的东西"。现方案:默认自治,但对不确定需求主动经邮箱 / 微信 claw 通知用户确认,并保留 **PRD 签署**、**部署前验收(强制)** 两个硬检查点。自治是默认态,升级是安全阀,二者正交。
2. **最难的不是编排,是 PRD 质量 + 自验收。** 小白给垃圾需求,PM 澄清引擎要极强;主程 / PM 无用户介入的自验收 = StrictRunner + 测试闸门在**产品尺度**的风险最高环,最易翻车。
3. **赛道拥挤。** Lovable / Bolt / Devin 已占"小白 → 应用"心智。VAT 若只拼"也能从一句话出应用",必被碾压。唯一能拼的是"**越用越懂你业务的长期乙方**"——即技能沉淀,不是首轮出活速度。
4. **首轮体验 vs 长期价值矛盾。** 用户首轮感知"出活快慢",而 VAT 护城河在"第 5 次比第 1 次聪明"。需在首轮就给"可接管 / 可审计"信任感来兜底慢热。

## 六、验证优先级(颗粒度, 接前文件 P0)

- **P0**(同前):1 角色验证压缩自检 ≥80%(记忆 / 技能真能复用,非文件夹管理)
- **P0.5**(新增):**单垂直跑通 需求 → PM·PRD → 主程拆 → 1 开发 → 测试 → 部署 全环一次**(哪怕只 1 个 dev 角色),证明闭环能端到端转,而非只验证记忆
- **检查点**:PRD 签署 + 部署前验收 **必须保留人工钩子**(哪怕默认自动过,留 override)
- **技能库验证**:第 2 个同类任务启动时,自动召回第 1 个蒸馏的 skill,评估"复用是否真降本 / 提质"

## 八、用户绑定与升级确认机制(新增)

> 解决 §五 #1 的"完全不需介入陷阱":默认自治,但对**不确定需求**主动通知用户确认,把"甲方失联"变成"甲方可随时被叫应"。

### 8.1 用户绑定层
- 绑定方式:**邮箱(email)+ 微信推送(企业微信 / 微信 claw bot)**,二者并列、失败互备。
- 存储:`users/<user-id>/binding.json` { email, wechat_claw_id, notify_prefs, default_action }
- 通道适配:`adapters/notify/` 统一 `NotifyProvider` 接口,email + wechat 实现并列,下行互备、上行(用户回复)统一回 `in/` 邮箱。

### 8.2 升级触发条件(精准,避免通知疲劳)
只在**真决策点**触发,日常歧义系统自循环消化:

| 触发点 | 触发条件 | 动作 |
|---|---|---|
| PRD 阶段 | 需求歧义 >N 处 / 范围无法自决 / 关键验收标准缺失 | 推送"需求确认卡"(多选项 + 说明) |
| 主程拆分 | 跨角色依赖冲突 / 技术选型无先例 | 推送"拆解决策卡" |
| 验收卡住 | 主程 / PM 自验收未过且回退 ≥2 次仍失败 | 推送"堵塞上报卡" |
| 首次公网部署 | 首次部署到阿里云 / 腾讯云等公网服务器 | **强制"部署授权确认"**(安全边界,不可跳过) |
| 不触发 | 单文件实现细节 / 命名 / 常规测试失败 | 系统自循环解决,不扰民 |

### 8.3 确认超时策略(关键)
- **默认 = 阻塞等待**:未经确认不擅自推进(甲乙方模式中擅自推进 = 风险)。
- **默认授权开关**:用户可设"低风险自动过,仅高风险上报" → 兼顾自治与可控。
- **超时 SLA**:可设(如 24h 无响应)按 `default_action`:要么自动驳回走保守方案,要么沿用上一次同类决策。避免无限挂起。

### 8.4 与"完全不需介入"的关系
自治是**默认态**,升级是**安全阀**。两者正交:日常 95% 路径零打扰,仅 5% 决策点叫应甲方。这比"纯自治"稳,比"纯人工"省。
